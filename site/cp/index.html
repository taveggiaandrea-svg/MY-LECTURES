What does numpy add to Python?

Why plain Python is slow with numbers, what numpy, scipy and matplotlib add, and how an integer with a fixed number of bits can turn a power of 3 into a negative number.

Type the same power twice in the console: once with an ordinary Python integer, once with a numpy integer. This is the lecture's first experiment.

In [2]: a = 3                # python integer
In [3]: a**100
Out[3]: 515377520732011331036461129765621272702107522001
In [4]: b = np.int64(3)      # numpy integer
In [5]: b**100
RuntimeWarning: overflow encountered in long_scalars
Out[5]: -2984622845537545263
In [6]: a == b               # and yet...
Out[6]: True

The warning is how the slides, made with an older numpy, show the session; current numpy (version 2) prints the same number without any warning, which makes the trap even quieter. A RuntimeWarning is a message numpy prints while the program keeps running.

Two numbers that compare equal give two different answers, and one of them is negative, although no power of 3 can be. The lecture's comment is short: equality is not identity. a and b hold the same value but are objects of different types, and the two types do arithmetic differently.

Repeat the experiment for every power from 31 to 3100 and the pattern appears.

The break happens exactly where the true power passes the largest value an int64 can hold. By the end of this lesson you will know why. First, a simpler question: why does numpy exist at all?

Easy to write, slow to run

Python was first released in 1991: the slides place it after the programming languages FORTRAN, C, C++, R and MATLAB and before Java, C# and JavaScript. On R the slide is inaccurate: R first appeared in 1993, after Python (its ancestor, the language S, dates from 1976). It was designed to be easier, more concise, more readable and safer than the alternatives, so that programs can be written and changed quickly, and it is now among the four most used languages, with C, C++ and Java.

The slides compare the two ways of building a list of the first n squares. In C:

int *l, i;
l = calloc(n, sizeof(int));
assert(l != NULL);
for (i = 0; i < n; i++) {
    l[i] = i*i;
}
/* use l here */
free(l);   /* need to clean up */

In Python:

l = [i**2 for i in range(n)]
# use l, no clean up needed

In C you declare every variable in advance and manage memory yourself: you work close to the hardware, with a lot of control and a lot of work. Python manages these things for you and has many common operations built in; the slides single out text strings as a case where C is horrible and Python is great.

The price is speed. Python is a general purpose language, meant for anything from computations to web servers to small scripts that tidy your files, and it was never designed to be particularly fast. Its design relieves the programmer of work, not the program. For most tasks that is fine, since a few hundredths of a second don't matter. In data science they do: the data are large and the algorithms take time.

A faster Python: numpy, scipy and matplotlib

People wanted a popular language with fast code, a library of scientific algorithms, all free and open source. MATLAB, a commercial language built for numerical computing, is closed and expensive; Julia is fast and free but young. So numpy was created, scipy was built on top of it, and matplotlib, inspired by MATLAB's plots, became their plotting companion.

From now on, every file and every session starts with the standard aliases:

import numpy as np
import matplotlib as mpl
import matplotlib.pyplot as plt

np.log(4 + np.exp(3))      # numpy functions carry the np prefix

numpy is a sort of language extension: numeric types for heavy computation (32-bit floats, 64-bit integers), a core type called the ndarray (N-dimensional array), a more efficient kind of list, mathematical functions and constants such as np.pi, and an alternative random module. scipy collects submodules for special functions, integration, optimization, linear algebra, statistics and signal processing: from scipy import special, then special.erf(1.5), the error function of statistics. sympy (symbolic mathematics) and pandas (data frames) complete the picture.

matplotlib draws plots. The slide's example calls plt.plot twice; in Spyder the plot appears at once, otherwise you call plt.show().

Why a numpy integer has a limit

Back to the opening. In Python an integer is, in principle, unlimited: it grows to as many digits as it needs. In numpy an integer has a fixed number of bits, for example 64. Each one takes a predictable amount of space, and the processor (CPU) can operate on it in a single instruction, often on 2 or 4 integers at once. That is much faster, and it is how the vast majority of languages treat integers. Python is the exception.

With \(\bits\) bits you can write \(2^{\bits}\) different patterns, so you can represent at most \(2^{\bits}\) different numbers. Take \(\bits = 4\): 16 patterns. If you want both negative and positive numbers, the convention gives the first half of the patterns, 0000 to 0111, to 0 to 7, and the second half, 1000 to 1111, to −8 to −1. If you only want non-negative numbers, the unsigned type uses all 16 patterns for 0 to 15.

\[ \text{signed: } -2^{\bits-1} \le x \le 2^{\bits-1}-1, \qquad \text{unsigned: } 0 \le x \le 2^{\bits}-1 \]

Now go one step past the largest value. There is no pattern left, so the count wraps around to the other end, like a car's odometer.

This is overflow: past the maximum or below the minimum, the numbers cycle around. In the 4-bit example you get bizarre results like 7 + 1 → −8 for the signed type, and 15 + 1 → 0 and 5 · 4 → 4 for the unsigned one, where everything is computed modulo 16 (the remainder after dividing by 16).

Overflow is not an error in the arithmetic: the result is right modulo \(2^{\bits}\), but read with the wrong sign or size. That is exactly what happened to b**100: the true result has 48 digits, numpy kept only its last 64 bits, and those bits, read as a signed number, start with a 1, so the value is negative.

The types that really exist

The 4-bit type does not exist; it only makes the wheel small enough to draw. The smallest real type is int8, from −128 to 127. Its unsigned twin uint8, from 0 to 255, is common in image data, where each pixel's brightness takes one byte. The others double the number of bits each time. The core type: the ndarray

An ndarray is homogeneous: all its elements have the same type. The slides call this statement imprecise but close enough to the truth for now. A 1-dimensional array looks like a Python list, but all its elements share one type (all 64-bit integers, or all 32-bit floats, or all booleans) and its size is fixed. It can behave like a mathematical vector. A 2-dimensional array is a table of numbers that can behave like a matrix. You can have as many dimensions as you like: 1 or 2 suffice for simple cases, while 3 or 4 are not unusual in machine learning and computer vision.

In [2]: a = np.array([4,6,8])
In [3]: type(a)       # the type name is ndarray
Out[3]: numpy.ndarray
In [4]: a[0]          # indexed like standard lists
Out[4]: 4
In [5]: type(a[0])    # but the type is not int!
Out[5]: numpy.int64

The element a[0] prints as 4 but is a numpy.int64, the same kind of integer as b in the opening, with the same 64-bit limit. And if the list mixes types? The course's second exercise tries it, and numpy picks one type that can hold every element.

A 2-dimensional array needs two indices per element, row first and column second, and carries three attributes that describe its form.

Fixed type and fixed size are restrictions compared with a list. Lesson 2 shows what they buy: because every element takes the same number of bytes, the computer can find any element without searching.

Lesson 2 · L. Saglietti, handwritten notes Storing arrays in memory, slides and first demo

How does an array live in memory?

Memory as a line of bytes, the header that tells the CPU how to read them, why a Python list is an array of pointers, and how a table is flattened row by row.

Lesson 1 claimed that numpy is fast because its numbers have a fixed number of bits, and that an ndarray has one type and a fixed size. To see why those restrictions buy speed, you need a picture of where data actually sit.

A line of bytes with no labels

The computer must write everything it processes or stores somewhere: in the RAM (random access memory), which behaves like a linear container. It is a long row of slots of 1 byte each, where a byte is 8 bits. Every slot has a number, its address: 0, 1, 2, 3 and so on, for billions of slots, since a gigabyte (GB) is \(10^9\) bytes. All computers are organized this way nowadays.

The bits always have a state, 0 or 1, left there by past computations or by random initialization. Now the lecture's question: what is the most natural way to store a sequence of numbers, say [2, 14, 3, 8], in this memory?

The notes put it plainly: there is nothing special about these bits, unless something points there.

Numbers as bits

First, how does a number become bits? In binary representation each of the 8 positions of a byte stands for a power of 2, from \(2^7 = 128\) on the left down to \(2^0 = 1\) on the right. A number is the sum of the powers whose bit is 1. All four numbers of the list fit in one byte.

\[ 14 = 0\cdot 2^7 + 0\cdot 2^6 + 0\cdot 2^5 + 0\cdot 2^4 + 1\cdot 2^3 + 1\cdot 2^2 + 1\cdot 2^1 + 0\cdot 2^0 \]

The natural idea is then to use consecutive slots of the RAM, one byte per number. But, as the opening figure shows, consecutive bytes alone don't answer two questions: where does the sequence start, and where does it end?

The header tells the CPU how to read

numpy's answer is a small block of information placed in front of the data, the header. It records the length of the array and the type of its elements. Your Python variable does not contain the array: it contains the address of the header. An address stored somewhere to reach something else is called a pointer (or reference, or arrow, as the notes say).

Why does the header need the type? Because the type fixes how many bytes each element takes: in a uint8 array each element takes 1 byte, in a uint32 array 4 bytes. The same bits read with a different type give different numbers.

The second panel is added on this page; the notes only state that a uint32 element takes 4 bytes. Its number assumes the byte order of common PCs, called little endian: the first byte is the least significant, so the value is 2 + 14 · 256 + 3 · 256² + 8 · 256³ = 134,417,922.

Homogeneous entries, plus the length and the type in the header: now the CPU knows how to read the content. As a consequence (spelled out here, not in the notes), element number i starts exactly i times the element size after the start of the data, so the CPU can compute where it is instead of searching for it.

Could a list use the same trick?

A Python list could be stored the same way: a header, then the values side by side. The notes show two reasons why it would not work, both coming from what lists allow.

Flexible assignment. In a list you can replace 3 with 3**100. That number needs many more bits (159 of them, so 20 bytes, a count added here), so everything after it would have to move to make room. The cost would be O(N), read "order N": proportional to the length N of the list. You want O(1): a constant cost, whatever the length. Flexible type. You can also replace 3 with the string "a". How would the program know how to interpret those bits?

Python's solution adds a layer: a list is an array of pointers, 64 bits each, and every pointer leads to an object stored elsewhere, with its own small header saying what it is (an int, a str, and so on).

The price: fetching an element of a list takes two jumps, one to the array of pointers and one to the object, while assignment becomes O(1): write the new content somewhere else and update the pointer. The type travels with each object, so any mix of types is allowed.

The notes end with a last argument for fixed types. In int64 + float64, as in 1 + 2.5, the CPU must first convert the integer to a float; in 1.0 + 2.5 it adds directly. Same result, but not the same operation. When every element has the same type, the operation is known once for all of them.

A table in a line

The RAM is 1-dimensional, but a matrix such as [[1, 2, 5], [3, 14, 7]] is 2-dimensional. The notes first show a possible way that is not how numpy does it: store each row as a separate vector, and link them with an array of pointers. This is indeed similar to how Python stores a list of lists: one more layer of pointers. numpy instead groups all the data in contiguous slots behind a single header, which now needs more information.

The shape is (number of rows, number of columns), here (2, 3); in general it is a tuple with one entry per dimension. One question remains: in what order are the six values written?

Row-major order goes row by row: the whole first row, then the second. C, C++ and Python (numpy's default) use it. Column-major order goes column by column, as in Fortran, MATLAB and Julia. One is the other applied to the transposed matrix (rows and columns swapped).

Why ndarrays are faster than lists

The slides call this "a very coarse-grained and imprecise discussion", but it explains the core. Take three lines that add up the elements of l:

s = 0
for x in l:
    s += x

If l is a list, Python has no way of knowing what its elements look like: integers, floats, lists, anything. Each time the third line runs, Python checks the type of x, then the type of s, then looks for the right method to call (__add__, __radd__, __iadd__). Adding two integers and adding two floats are different machine instructions, the type of s may change at every step, and Python may need to raise an error if a string turns up.

If you know in advance that every x is an integer, all that work disappears. Most of the gain, though, comes from the methods numpy writes in C, such as a.sum() for those three lines. (The slide writes l.sum(), but a list has no sum method; the method belongs to an ndarray.) They exploit the fixed type and work on a contiguous block of memory without following pointers. Working with ndarrays lets your code work in bulk. (Python also has optimizations for lists; the principle stands.)

The lecture's first demo, 0_rand_sum_demo.py, measures this: it creates a million random numbers as a list and as an array, and sums both.

l = [random.random() for i in range(n)]   # python list
a = rnd.rand(n)                            # numpy array (numpy.random as rnd)
s_list = sum(l)
s_array = a.sum()

The second demo begins: estimating π

The lecture ended by starting a second demo, completed in lesson 3. The idea: throw random points into the unit square, from 0 to 1 on both axes. The quarter of the unit circle inside it has area π/4, and the square has area 1, so a uniformly random point falls inside the quarter circle with probability π/4. Counting the points that fall inside gives an estimate of π.

The first step is drawing the quarter circle with matplotlib. The script samples equally spaced angles between 0 and π/2 and turns each into the point (cos θ, sin θ). The commented-out version does it with a list and a loop; the version kept uses arrays.

num_points = 100
theta = np.linspace(0., np.pi/2, num_points)   # equally spaced angles
xs = np.cos(theta)                             # cos of every angle at once
ys = np.sin(theta)
plt.clf()
plt.plot(xs, ys, color="red")

Notice that np.cos(theta) computes 100 cosines in one call: the function is applied to every element. Lesson 3 turns that habit into a rule.

Lesson 3 · L. Saglietti, the π estimation demo and the slides on broadcasting, indexing and views

How do you compute on a whole array at once?

Monte Carlo estimation of π without loops, the broadcasting rules, the four ways to index an array, and the difference between a view and a copy.

Lesson 2 ended with the quarter circle drawn from 100 equally spaced angles, and with the plan: throw random points into the unit square and count how many fall inside the quarter circle. That method is called Monte Carlo: estimating a quantity by drawing many random samples. Here is the experiment.

A uniform point lands inside with probability equal to the area of the quarter circle, π/4, divided by the area of the square, 1. So the fraction of points inside estimates π/4, and four times that fraction estimates π:

\[ \piest = 4\,\frac{\Nin}{\Npts} \]

where \(\Npts\) is the number of points and \(\Nin\) the number that fall inside.

From a loop to one line

The script 01_pi_estimate.py keeps the first attempt as comments: a loop that draws one point at a time and counts it if it falls inside.

ninside = 0
for i in range(n_mc):
    px = np.random.random()
    py = np.random.random()
    if px**2 + py**2 <= 1:
        ninside += 1

The version that the lecture kept does the same with no loop at all:

pxs = np.random.random(n_mc)          # n_mc random x coordinates at once
pys = np.random.random(n_mc)
ninside = np.sum(pxs**2 + pys**2 <= 1)
print(f"estimated pi = {4 * ninside / n_mc} real pi = {np.pi}")

Read the third line from the inside. pxs**2 squares every element. The + adds the two arrays element by element. <= 1 compares every element with 1 and returns an array of booleans. np.sum adds the booleans, where True counts as 1 and False as 0, so it counts the points inside.

Operations that apply element by element

The line above works because of a mechanism that basically every numpy function uses, called broadcasting. In full generality it can be confusing until you get used to it; at the most basic level it just means that operations are applied element-wise.

Take two arrays a and b of the same shape. a + b gives the element-wise sum: not what happens with Python lists, where + concatenates. a * b gives the element-wise product, which is not the matrix product of linear algebra (unlike MATLAB). The same holds for every operator, such as a**b, and for numpy's versions of sin, log, exp: they return an array of the same shape, with the function applied to each element.

In [2]: a = np.linspace(1.0, 2.0, 6)    # [1. , 1.2, 1.4, 1.6, 1.8, 2. ]
In [4]: b = np.ones(6)
In [6]: a + b                           # element-wise, NOT concatenation
Out[6]: array([2. , 2.2, 2.4, 2.6, 2.8, 3. ])
In [9]: a > b
Out[9]: array([False,  True,  True,  True,  True,  True])
In [10]: a == b                         # even == broadcasts
Out[10]: array([ True, False, False, False, False, False])
In [11]: np.array_equal(a, b)           # are the arrays equal?
Out[11]: False

One surprise: comparisons broadcast too, even == and !=. They return an array of booleans, not a single True or False. To ask whether two whole arrays are equal, use np.array_equal.

When the shapes differ

Broadcasting really earns its name when the shapes are not the same. With an array a and a scalar x, x * a or a ** x applies the same x to each element: the scalar is expanded, as if it were an array of the same shape full of copies. Again unlike lists, where a * 3 would repeat the list three times.

With a 2-d array of shape (n, p) and a 1-d array of shape (p,), the 1-d array is expanded into a 2-d array with identical rows. A shape (3,) is equivalent to (1, 3), or (1, 1, 3), and so on. A column of shape (2, 1) is expanded along the other direction, so (2, 1) and (1, 3) together become (2, 3).

In [3]: a = np.array([[3,4,0],[1,2,2]])
In [4]: b = np.array([2,4,0])
In [5]: a * b                   # not a matrix-vector product
Out[5]: array([[ 6, 16,  0],
               [ 2,  8,  0]])

A note on the source: in the slides' scalar example, a is [1., 1.2, 1.4, 33., 1.8, 2.] and a**2 correctly gives 1089 for the fourth element, but a*3 is printed as [3., 3.6, 4.2, 4.8, 5.4, 6.]. The fourth element should be 99, three times 33: 4.8 is three times 1.6, probably the value before it was changed to 33.

The slides close with the general rule, for any number of arrays and dimensions.

Broadcasting rules. First, arrays with fewer dimensions are padded with extra dimensions of size 1 at the beginning, until all have the same number of dimensions. Second, along each axis take the largest size n: every array must have either size n or size 1 there, and a size 1 is repeated n times. Third, the operation is applied element-wise.

Broadcasting never copies data: it lines the shapes up from the right and stretches the sizes equal to 1. The same idea works in assignment. a[:,:] = 2.0 sets every element, like fill; a[0:2, 0:3] = [1,2,3] writes the row [1,2,3] into both rows of a 2 × 3 block. You can even operate with an array and a list: the list is treated as a 1-d array.

π in more dimensions, and how good the estimate is

The lecture left four tasks: draw the square too, generalize the estimate to higher dimensions, study how the estimate scales with the number of points, and plot only the points that fall inside. The opening figure already does the first and, with its colours, a version of the fourth: plotting only the inside points is plt.plot(pxs[mask], pys[mask], ".") with mask = pxs**2 + pys**2 <= 1, a mask index you will meet below. The course solution, 02_mc_pi_est_proj.py, handles the second and the third.

In \(\dimd\) dimensions you draw points in the unit cube and count those inside the unit ball. The ball's volume is \(V_{\dimd} = \pi^{\dimd/2} / \Gamma(\dimd/2 + 1)\), where \(\Gamma\) is the gamma function, which extends the factorial (\(\Gamma(k+1) = k!\)). The cube from 0 to 1 holds only one of the \(2^{\dimd}\) symmetric sectors of the ball, so the fraction of points inside estimates \(V_{\dimd}/2^{\dimd}\). Solving for π:

\[ \piest = \left( 2^{\dimd}\, \Gamma\!\left(\tfrac{\dimd}{2}+1\right) \frac{\Nin}{\Npts} \right)^{2/\dimd} \]

With \(\dimd = 2\) this is the formula of the opening, since \(\Gamma(2) = 1\). The code is still one line of counting:

ps = rnd.rand(dims, n)                         # rnd is numpy.random; one column per point
ninside = ((ps**2).sum(axis=0) <= 1).sum()     # squared length of each point, then count

For the scaling analysis, the solution repeats each estimate many times with different random numbers and records the mean and the standard deviation (the typical size of the deviation from the mean).

The bars shrink like \(1/\sqrt{\Npts}\): ten times more precision costs a hundred times more points. In higher dimensions they grow, which the solution flags with "it gets worse!!! why? think about it". The fraction of the cube inside the ball collapses: about 79% of points in 2 dimensions, 52% in 3, but only 0.25% in 10, so 10,000 points leave about 25 inside to count.

Picking pieces: four ways to index

An ndarray can be indexed with the same syntax as Python lists. You can use slices, such as 0:5:2 or just :, and negative indices that count from the end, along each dimension: if a is 2-d, a[0, 0:5] gives row 0 and columns 0 to 4, and a[1:3, :] gives the sub-matrix of rows 1 and 2 with all columns.

Two more ways are not available for lists. Take a = np.array([6, 2, 8, 1, 7, 3]). Indexing with a list of positions, a[[0, 2, 3]], gives [6, 8, 1]. Indexing with a boolean mask, one True or False per element, picks the elements marked True: a[np.array([1,0,1,1,0,0], dtype=bool)] gives the same [6, 8, 1]. You can mix any method along any dimension, as in a[1:3, [2,4,5]].

A note on the source: the slide's mask is [1,0,1,1,0,0,0], with seven entries for a six-element array. Real numpy refuses it with an IndexError: a boolean mask must have exactly as many entries as the axis it indexes. The six-entry mask above is the corrected version.

The four kinds of index do not behave the same way when you write into the result. That difference is the most important point of the lecture.

Views and copies

When you index with slices, what you get is a view: an ndarray that shares the same data as the original. In the language of lesson 2 (a picture added here): a view is a new header that points into the same block of data, possibly reading it in strides, for example every second element; the slides note that different ndarrays can share data, or just part of it. Writing into a view writes into the original.

In [4]: b = a[0:5:2]           # view of a, every other element
In [6]: b[1] = 999             # this changes both a and b!
In [7]: a
Out[7]: array([  0,   1, 999,   3,   4])
In [8]: c = a[0:5:2].copy()    # how to get a new array
In [9]: a.base is not None     # is a a view? no
Out[9]: False
In [10]: b.base is a           # b is a view of a
Out[10]: True

Every ndarray has a .base attribute: None if the array owns its data, the original array if it is a view. .copy() gives you independent data. Slices are not the only source of views: the methods reshape(), which gives the same data a new shape, and ravel(), which flattens it, also return views. A view of a view is still a view of the original.

And the three dots ... stand for "all the remaining dimensions": m[3, ..., 4] is m[3, :, 4] in 3-d. They are seldom useful.

Lesson 4 · L. Saglietti, slides Optimization and greedy approaches

What makes an optimization problem hard?

Optimization problems, the space of configurations and its neighbourhoods, greedy search and its local minima, and why the obvious strategy often fails.

Lessons 1 to 3 built the numpy toolbox. From here on, the course uses it for its main thread: optimization, finding the best option among very many. The slides open with a small world of 13 options, each with a cost, where some options are "close" to each other.

The search never made a bad decision: every step it took went downhill. Yet it ended at 0.5 instead of 0.2. This lesson explains why, and what can be done about it.

What an optimization problem is

Optimization problem. Given a function \(c: X \to \mathbb{R}\), where \(X\) is any set, find the value \(x\) in \(X\) such that \(c(x)\) is minimum.

\(c\) is the cost and \(X\) the set of possible configurations. If you want a maximum instead, minimize \(-c(x)\): the slides stick with the minimum from now on. In simpler cases \(X\) is \(\mathbb{R}^d\), the set of lists of \(d\) real numbers: think of a cost in money, time or energy that depends on \(d\) parameters. Even that can be very hard when \(c\) is not a "nice" function, as the second half of the course will show.

Usually there are extra restrictions, so \(X\) is only a subset of \(\mathbb{R}^d\). A parameter may have a limited range, such as a fraction of resources invested, between 0 and 1. Two parameters may interact: two such fractions cannot add up to more than 1. The restrictions can get arbitrarily complicated.

A discrete optimization problem is one where \(X\) is discrete. The slides' example: in a map of cities and roads (a weighted directed graph: points joined by one-way arrows, each with a length), find the shortest path from city A to city B. The course focuses on \(X\) discrete and finite, so \(c(x)\) takes only a finite number of values.

Things get interesting when \(X\) is very large. Its elements are usually made of pieces: a path is made of edges, and the number of paths grows exponentially with the size of the graph. Another simple case is the set of binary strings of length \(n\), a sequence of \(n\) true or false decisions, which has \(2^n\) elements.

Checking every configuration often scales like O(2n): adding one piece doubles the work. Exhaustive search is out of the question; something smarter is needed.

Greedy: always go downhill

Suppose you have a notion of neighbourhood in \(X\): given two configurations, you can tell whether they are "close". In the graph example, two paths from A to B are neighbours if they differ only by one intermediate node. In the binary string example, two strings are neighbours if they differ in one bit.

A greedy approach then goes like this. Pick an initial guess \(x_0\), maybe at random. At every time step, pick a neighbour \(y\) of the current \(x_t\), maybe at random. If \(c(y) \le c(x_t)\), move there: \(x_{t+1} = y\); otherwise stay: \(x_{t+1} = x_t\). Keep going until you reach an \(x\) whose neighbours are all worse.

Local minimum. A configuration whose neighbours all have a higher cost. The configuration with the lowest cost of all is the global minimum.

The lecture's first sketch of the code is exactly this, with the pieces still to write marked TODO:

def greedy(..., num_iters):        # TODO decide arguments
    x = init_config()              # pick a configuration at random
    for t in range(num_iters):
        y = propose_move(x)        # propose a move
        if cost(y) <= cost(x):     # accept it if it does not worsen the cost
            x = y
    return x

In the opening graph, 6 and 4 are local minima and 9 is the global minimum. From 10 the search could have gone to 9, but the neighbour it drew at random was 6, which was also downhill. Once at 6, every neighbour is worse, and greedy is stuck. A greedy approach is quick and relatively easy to implement, and it often gives very poor results.

Two ways out

The slides suggest one easy fix: multiple attempts, or restarts. Run greedy many times from different random starting points and keep the best result. In the opening graph, where greedy ends depends on the start and on the luck of the draws, and some starts can never reach 9.

From 1, 4, 6 or 8 the answer is never; from 13 it is certain. Averaged over the 13 starts, one run succeeds with probability 5/13, about 38%, and \(k\) independent runs fail together with probability \((8/13)^k\). Ten restarts already give 99%. A comment added here: on real problems the number of local minima typically grows with the size, and restarts become a lottery with very long odds.

The slides' second idea is the deeper one: things might need to get worse before they get better. To go from 6 to 9 you must first accept a step uphill, to 5 or 10; from the other local minimum, 4, the way to 9 passes through 7, uphill again. Greedy never does. The course will build a method that sometimes does, simulated annealing.

What a greedy program needs

To code random-search greedy for a real problem you must be able to do five things. Represent a configuration \(x\) in the computer's memory: choose a representation. Compute its cost, which may be expensive but is not itself a problem. Pick an initial configuration at random. Pick a random neighbour of any configuration: propose a move. And decide whether the new configuration is better, using the delta-cost, the change in cost that the move would cause.

Why not just compute the new cost and compare it with the old? You can, but it is often much more efficient to compute only the difference. In the path example, change one intermediate node of a route from A to B.

Removing an intermediate node, or adding one, works the same way. In general you want a local move to cost O(1) to evaluate: a constant amount of work, however large the configuration. The lecture implements exactly this in lesson 5.

Another greedy: build one piece at a time

"Greedy" is a loose term, not a well-defined class. A second kind applies when configurations are made of pieces and the cost can be computed on a partial configuration. A path that starts at A and has not yet reached B still has a length; a cost on binary strings may be computable on just the beginning of a string.

Then you can build a solution one piece at a time, each time taking the option with the lowest cost so far: partial buildup. In the graph, take the shortest edge out of A, then the shortest out of the next node (without going back), and so on, hoping to reach B. With strings, choose the first bit; say 0 is better. Then choose between 00 and 01; say 01. Then between 010 and 011, and so on.

The cheap first step leads into an expensive neighbourhood: 0.3 + 0.8 + 0.3 + 1.2 = 2.6, against 0.5 + 0.3 + 0.5 + 0.3 = 1.6 for the best path. Same verdict as before: very quick, usually easy to implement, often very poor results.

Don't be greedy

For some selected problems there are sophisticated approaches that are not greedy. For the best path from A to B there is Dijkstra's algorithm, a classic method that finds shortest paths in a graph exactly. The course will meet dynamic programming, which solves the left-to-right route example above exactly.

For other problems no fast algorithm that guarantees the optimum is known, and likely none will ever exist. These are the NP-complete (NP-C) problems and harder ones: a family of problems such that a fast exact method for any one of them would give one for all, and decades of effort have found none. For them the course studies an approximate but general approach, a metaheuristic (a general strategy that can be adapted to many problems) called simulated annealing.

The first test case is the most famous NP-complete problem of all: the travelling salesman.

How do you search for a short TSP route?

The travelling salesman problem, a route stored as a permutation, the swap-paths move, a delta-cost in O(1), a distance matrix built with broadcasting, and random restarts.

Lesson 4 described random-search greedy in the abstract and listed what it needs: a representation, a cost, a random start, a move and a delta-cost. The lectures then wrote all of it for one concrete problem. This is the result at work.

Every change you saw was the same small move, accepted only when it made the route no longer. This lesson builds that program piece by piece, following the lectures' versions of the code.

The travelling salesman problem

The travelling salesman problem (TSP) is a celebrated NP-complete problem: there is no known efficient way to reach the optimum in the worst case.

TSP. Given \(n\) cities and the distance \(d_{ij}\) between any two cities \(i\) and \(j\) (symmetric: \(d_{ij} = d_{ji}\)), find the shortest route that goes through every city exactly once and goes back to the starting point.

The slides call such a route a "shortest Hamiltonian path on a graph"; since it closes on itself, the usual name is a Hamiltonian cycle. In the language of lesson 4, \(X\) is the set of all such routes and \(c(x)\) is the total distance along the route. How large is \(X\)? There are \(n!\) ways to order the cities, but the same loop can start from any of its \(n\) cities and run in either of 2 directions:

\[ |X| = \frac{n!}{2n} \]

The slides also show a map of a large TSP instance over the United States, a picture not reproduced here. The table makes the same point: checking every route is hopeless already for a few dozen cities.

Two greedy ideas

The first is partial buildup: start from a random city, go each time to the closest city not yet visited, and when all are visited go back to the first. It is called the nearest neighbour heuristic. The slides' verdict: "this works awfully".

The second is random-search greedy, the one the lectures implement. It needs two decisions. How do you represent a route? A permutation of the cities' indices works fine. When are two routes neighbours? There are several possibilities; the course uses the swap-paths rule: from any route, pick two edges i → j and l → k and swap them to i → l and j → k.

A route is a permutation

The lecture starts by representing the problem: a class Cities (later renamed TSP) that stores n and random coordinates in the unit square, with an optional seed so that the same cities come out every time, which helps a lot with debugging.

class Cities:
    def __init__(self, n, seed=None):
        if seed is not None:
            np.random.seed(seed)
        self.n = n
        self.x = np.random.rand(n)         # coordinates uniform in [0,1) x [0,1)
        self.y = np.random.rand(n)

def init_config(cities):
    return np.random.permutation(cities.n)  # a random route

A route is an array that lists the cities in the order they are visited. The e-th edge joins route[e] and route[e+1], and the last one, edge \(n-1\), joins the last city back to the first. A single formula covers both cases with the modulus: edge e joins route[e] and route[(e+1) % n], because \((n-1+1) \bmod n = 0\).

The display function needs the coordinates in route order: x[route[0]], x[route[1]], …, which is exactly x[route], indexing with an array as in lesson 3. The comeback edge is drawn separately at first; the task left in the code, solved in 09_TSP.py, uses the modulus to draw everything in one call: plt.plot(x[route[np.arange(n+1) % n]], y[route[np.arange(n+1) % n]]). The index array is 0, 1, …, n−1, 0.

The swap-paths move

Picking edges i → j and l → k and reconnecting them as i → l and j → k has a side effect, noted on the slide: the piece of route from j to l gets reversed. In the array, that piece is a contiguous block, so the move is a reversed slice.

new_route = route.copy()
new_route[e1+1:e2+1] = new_route[e2:e1:-1]   # reverse the block between the two edges

The right-hand side reads from e2 down to e1+1 with step −1 (the stop e1 is excluded), and it is written into positions e1+1 to e2. With e1 = 1 and e2 = 5, positions 2 to 5 are reversed, as in the figure.

Not every pair of edges gives a real move. The code draws e1 and e2 at random, sorts them, and redraws until three bad cases are excluded: the same edge twice (e1 == e2), two adjacent edges (e1 + 1 == e2), and the special adjacent pair at the end of the route, edge \(n-1\) and edge 0, caught by (e2+1) % n == e1. In each of these cases the "new" route would be the same loop as the old one. (The commented final copy of the code writes the last test as not (e1 == 0 and e2 == n-1), which is equivalent once e1 < e2.)

while True:
    e1 = np.random.randint(n)
    e2 = np.random.randint(n)
    if e1 > e2:
        e1, e2 = e2, e1
    if e1 != e2 and e1+1 != e2 and (e2+1) % n != e1:
        break

The cost, and only what changes

The cost walks along the route and adds the length of every edge, the comeback included thanks to the modulus. It does \(n\) additions: O(n).

def cost(cities, route):
    n = cities.n
    c = 0.
    for i in range(n):
        c += cities.dist(route[i], route[(i+1) % n])
    return c

The first delta-cost is the naive one: cost of the new route minus cost of the old, O(n) per proposal. But lesson 4 promised O(1) for a local move, and the slide says why it is possible: only 4 edges are involved in the delta-cost computation. The two removed edges join route[e1] to route[e1+1] and route[e2] to route[e2+1]; the two added edges join route[e1] to route[e2] and route[e1+1] to route[e2+1]. The reversed block keeps the same length, since distances are symmetric.

\[ \Delta c = d(c_{11}, c_{21}) + d(c_{12}, c_{22}) - d(c_{11}, c_{12}) - d(c_{21}, c_{22}) \]

Here \(c_{11}, c_{12}\) are the two cities of the first edge and \(c_{21}, c_{22}\) those of the second, the names used in the code. The greedy loop accepts the move when \(\Delta c \le 0\) and updates the running cost with c = c + delta_c, without recomputing it.

All the distances at once

The delta-cost asks for distances again and again, and computing each one from the coordinates means a square root every time. Since the cities never move, the final version computes all the distances once, in the constructor, and stores them in an \(n \times n\) matrix: dist[i, j] is the distance between cities i and j. The matrix is symmetric, with zeros on the diagonal.

The first version uses a double loop over the upper triangle and copies each value to its mirror. The second uses broadcasting, as in lesson 3: subtracting a column of shape (n, 1) from a row of shape (n,) gives the (n, n) matrix of all pairwise differences.

xT = x.reshape((n, 1))                       # column copies of the coordinates
yT = y.reshape((n, 1))
self.dist = np.sqrt((xT - x)**2 + (yT - y)**2)   # (n,1) with (n,) broadcasts to (n,n)

(The commented final copy writes x - xT: the sign of each difference flips, the squares do not.)

With the matrix, self.dist(city1, city2) becomes the lookup self.dist[city1, city2]: the lecture calls this "using the memory to speed up even further".

Random restarts

Lesson 4's easy fix for local minima is multiple attempts. The lecture adds a restarts argument to greedy (called repeats in the commented final copy): each restart picks a new random route, runs the loop, and if its final cost beats the best so far, stores it away. The course scripts run 200 cities with 5 restarts of 200,000 iterations, and 100 cities with 30 restarts of 50,000 iterations.

best_c = np.inf                      # placeholder: any real cost is smaller
for i in range(restarts):
    x = init_config(cities)
    c = cost(cities, x)
    for t in range(num_iters):
        y = propose_move(x)
        delta_c = compute_delta_cost(cities, y, x)
        if delta_c <= 0:
            c = c + delta_c
            x = y
    if c < best_c:
        best_c, best_x = c, x

One detail in the lecture's version 2: the function ends with return x, the last restart's route, rather than the best one, best_x. The later versions return the best object, as they should.

How do you write an optimizer that works for any problem?

Separating the problem from the optimizer, an interface of seven methods, moves as tuples, changing data in place, shallow and deep copies, and the same solver applied to Latin squares.

Lesson 5 ended with a working greedy for the TSP, but written as loose functions: greedy(cities, ...) calls init_config(cities), cost(cities, route), propose_move(route). Look at what the main loop needs to know. Nothing in it is about cities: it proposes, measures, accepts. The lectures' next step is to make that explicit, so that the same greedy can solve any problem.

Disentangling the problem from the optimizer

The refactored code (version 3) puts everything that is specific to the TSP inside a class, TSP, as methods: functions that belong to an object and receive it as their first argument, self. The optimizer receives an object probl and only calls its methods. Any class that provides the same methods can be optimized by the same code. The list of methods is the interface between the two.

The final version of the interface, as written at the top of Greedy.py, has seven methods.

MethodWhat it doesCost for the TSP (estimated here)

def greedy(probl, repeats=1, num_iters=10, seed=None, debug_delta_cost=False):
    best_probl = None
    best_c = np.inf
    for step in range(repeats):
        probl.init_config()
        c = probl.cost()
        for t in range(num_iters):
            move = probl.propose_move()
            delta_c = probl.compute_delta_cost(move)
            if delta_c <= 0:
                probl.accept_move(move)
                c += delta_c
        if c < best_c:
            best_c = c
            best_probl = probl.copy()
    return best_probl

The scripts keep the two halves in separate files, TSP.py and Greedy.py, which become modules: a file name without .py is the name you import. The run script does from TSP import TSP and from Greedy import greedy, then tsp = TSP(200, seed=45871231) and greedy(tsp, restarts=5, num_iters=200000, seed=1282323). The constructor also guards its input with raise Exception(...) when n is not a large enough integer, and the commented final greedy records last_accepted_t, the last iteration with an accepted move, a quick check of whether num_iters was enough.

Three design choices of this version deserve a closer look: the move is a small encoding rather than a new configuration, the configuration lives inside the object and is changed in place, and the best result is saved with copy(). Each of them comes from a problem with the previous version.

Proposing is not accepting

In lesson 5, propose_move(route) returned a whole new route: an O(n) copy for every proposal, even though most proposals are rejected. Version 4 splits the job in two. propose_move() only encodes the move, packing the two edge indices into a tuple, move = (e1, e2): O(1). compute_delta_cost(move) unpacks it and evaluates it, and only if the move is accepted does accept_move(move) actually reverse the block of the route.

The first delta-cost of the refactored code was still the naive, safe one: copy the whole problem, accept the move on the copy, compute the new cost, subtract. Version 5 replaced it with the 4-edge formula of lesson 5, marked in the code as "O(n) bottleneck → O(1)". The naive version did not disappear: it became a debugging tool.

if debug_delta_cost:
    probl_copy = probl.copy()
    probl_copy.accept_move(move)
    assert abs(c + delta_c - probl_copy.cost()) < 1e-10   # floating-point tolerance

The check relies on copy and accept_move, which are much easier to write correctly than an efficient compute_delta_cost. It is very slow, so it is switched on only while developing a new problem class. Write the slow, obviously correct version first, and use it to test the fast one.

The configuration lives inside the object

From version 4, the route is an attribute, self.route, created once in the constructor with np.zeros(n, dtype=int). Methods change its contents in place instead of building new arrays: init_config writes self.route[:] = np.random.permutation(n), and the greedy loop comments the call as "O(n) not allocating new memory".

Inside the methods the code often writes route = self.route to keep lines short. The commented version of the course warns about what that line means: route and self.route share the same data, but they are not the same variable.

The same applies to the local copies of the coordinates, x next to self.x: as the comments of the constructor put it, writing x = something would not affect self.x. Writing into a shared array (a[...] = ...) changes it for everyone; assigning to a name (a = ...) changes only that name.

Saving the best: shallow and deep copies

With restarts, the solver must remember the best configuration found so far while it keeps changing the current one in place. The obvious line, best_probl = probl, does not work: it makes a second name for the same object, which the next restart overwrites. So the lectures add a copy() method. But copying an object can mean two different things.

A shallow copy, copy.copy(probl), makes a new object whose attributes are the same values as the old one's: for an attribute that is an array, the new object points to the same array. A deep copy, copy.deepcopy(probl) from the module copy, duplicates everything recursively, arrays included.

That is why the course writes return deepcopy(self) in copy, with the comment that it "could be optimized (specialized for the problem)": a problem class could copy only the parts that change, here the route. The shallow copy fails precisely because the code changes arrays in place, the efficient choice of the previous section. The two decisions go together.

Drawing a fair move

The move proposal of lesson 5 draws e1 and e2 and redraws until the pair is valid. A task left in version 6 asks to do it without rejections, using the modulus; 09_TSP.py solves it (the commented copy in 11_more_comments.zip keeps the loop):

e1 = np.random.randint(n)
e2 = (e1 + 2 + np.random.randint(n-3)) % n   # skips e1-1, e1 and e1+1, cyclically
if e1 > e2: e1, e2 = e2, e1

Going around the ring of \(n\) edges, e2 lands anywhere from 2 to \(n-2\) steps after e1: never on e1 itself or on either of its two neighbours, the invalid cases, and on each valid edge with the same probability.

Exercise 2 of the course, "The wrong move", warns that a shortcut can look right and still be wrong. To draw two different indices with e1 < e2, its first method, like the lecture's code, redraws until the indices are acceptable and sorts them. (As printed on the sheet, that loop has lost its exit condition: without an if ...: break it would never stop. The official solution has if i != j: break.) A tempting alternative avoids the loop: e1 = np.random.randint(n-1), then e2 = np.random.randint(e1+1, n). Every pair it produces is valid, but not every pair is equally likely.

For greedy the bias only makes some moves come up more often than others. For simulated annealing, the exercise adds, the second code is "definitely wrong": the method assumes the moves are proposed with the right probabilities (the detailed balance condition, which the course meets with Markov chains). The exercise's rule of thumb: keep extracting moves randomly with a flat measure, and reject the invalid ones, until you get a good one.

Exercise 3 tries a different move for the TSP, swapping two cities along the route instead of crossing two edges (the sheet's "Call the indices 1 and j" means i and j). Its delta-cost is harder: more edges are involved, and the cases depend on whether the two cities are adjacent.

Same solver, different problem: Latin squares

The payoff of the interface is that a new problem needs only a new class. The exercise sheet's longest sequence uses Latin squares: an \(n \times n\) table in which every row and every column contains each number from 0 to \(n-1\) exactly once, like a Sudoku without the sub-squares. The configuration is the table; the cost counts the rows and columns that violate the rule, so the goal is cost 0.

Exercise 4 makes the obvious choices: a random table, and a move that changes one entry to a different value; the delta-cost only needs the affected row and column, checked with np.unique. It works for very small n, but at n = 15 it is very unlikely to succeed in any reasonable time.

Exercise 5 shrinks the search space instead. Start from a table in which every column already contains 0 to n−1 in order (cost n: every row is wrong), and move only by swapping two entries of the same column, so the columns stay valid and only two rows change. Exercise 6 changes a single line, the cost of a row: from "wrong or right" to "how many values are missing". Now the solver can tell an almost-correct row from a hopeless one, and performance improves dramatically, especially at larger n.

The sheet's conclusion holds for every problem in the course: what makes greedy work is the choice of representation, moves and cost function, not the loop, which never changed.
