What makes Spark so fast?

Lightning fast computing with Spark: in-memory processing, the cluster architecture, RDDs, transformations and actions, DataFrames and Spark SQL.

Lesson 5 ended with MapReduce: map close to the data, shuffle, reduce, and a result written to HDFS. It works, but it is slow and hard to program. Spark does the same kind of job, and the first slide of the lecture says how it differs.

Spark. A fast, in-memory data processing engine, with APIs in Scala, Java, Python and R. Running on Hadoop's YARN, it integrates deeply with Hadoop; on top of its core it powers a stack of high level tools: Spark SQL, MLlib for machine learning, GraphX for graphs and Spark Streaming.

Spark started in 2009 as a Hadoop subproject at AMPLab, became open source in 2010 and an Apache project in 2013; versions 1.6.2 and 2.0.0 came in 2016, 2.3 and 2.4 in 2018, 3.x in 2020. The slide places AMPLab at UCLA: it is the laboratory of the University of California at Berkeley.

Keep the data in memory between steps

Most real jobs have several steps: clean, then join, then aggregate, then iterate. MapReduce reads its input from HDFS and writes its output to HDFS at every step, and disks are slow. Spark reads once, keeps the intermediate results in memory and writes only at the end.

Spark is fast because it stops writing to disk between one step and the next. Not only: the lecture stresses that it is fast for on-disk computation too, as two benchmarks show.

Who does what in a Spark cluster

The driver program contains all the instructions Spark must execute, for example read a file, aggregate the data, save the result to another file. In it the programmer creates the SparkSession object, which connects to the cluster through a cluster manager and sends the program to be executed. Spark can use YARN as cluster manager if it lives on the same cluster as Hadoop, Apache Mesos, or its own standalone manager.

Once connected, the driver sends the lines of code with the Spark commands. The worker nodes, generally one per physical machine, receive them and allocate one or more executors: services running on the Java virtual machine (JVM) that create the tasks which physically execute the instructions, and allocate enough memory to each task. Executors on different workers exchange data when needed: these exchanges are the shuffles, and they happen when the program aggregates data (rows with the same key may sit on different workers) or sorts them.

The master parameter of the session decides which cluster to use, as in SparkSession.builder.master("spark://myserver:7077").appName("myApp").getOrCreate().

The Apache distribution is relatively easy to install on every operating system. Databricks offers another distribution, also in the cloud, and Spark is available as a cloud service on Microsoft HDInsight, Google Cloud and IBM Bluemix.

Data cut into partitions: the RDD

RDD. A resilient distributed dataset is the primary abstraction of Spark: an immutable, fault-tolerant collection of elements, cut into partitions that are distributed across the nodes of the cluster and processed in parallel.

Each partition is managed by an executor, generally one executor per node, and an executor can manage more than one partition of the same RDD. An RDD can hold strings, as when you read a text file, or key/value pairs, created by the program. It is created either from a file system (HDFS, HBase, or any Hadoop data source) or by parallelizing an existing Scala or Python collection.

Nothing happens until you ask for a result

Once an RDD exists, every operation on it is one of two kinds. A transformation creates a new RDD from an existing one and adds a step to the processing plan, the DAG (directed acyclic graph: the execution workflow of the program). An action executes the DAG and returns a value. Transformations alone compute nothing: Spark waits for an action, then runs the whole plan at once.

rdd = sc.textFile("input.txt")\
    .flatMap(lambda line: line.split())\
    .map(lambda word: (word, 1))\
    .reduceByKey(lambda x, y: x + y, 3)\
    .collect()

Read line by line: sc is the SparkContext of the session; textFile reads the file into an RDD of lines, flatMap splits the lines into one big RDD of words, map turns each word into a key/value pair (word, 1), reduceByKey groups by key and sums the values into 3 partitions, and collect returns the result to the driver. A lambda is a small function written inline.

A DAG is cut into stages at every shuffle, and the stages run in order. Inside a stage each partition goes through its steps on its own executor; at the boundary the data must be redistributed, so that all the pairs of one word meet in the same partition.

Tables again: DataFrames and Spark SQL

To Spark the elements of an RDD are opaque objects: their inner structure is unknown. Spark SQL is the module for structured data, and it adds the DataFrame: a distributed collection of data organized into named columns, conceptually equivalent to a table of a relational database or to a data frame in R or Python, with richer optimizations under the hood. It can also act as a distributed SQL query engine.

An RDD becomes a DataFrame in two ways, both in the course script: by declaring a schema (StructType with the field names and types) or by turning each element into a Row and letting Spark infer the schema. DataFrames are also read directly from data sources such as JSON files, JDBC connections (the Java standard for reaching a database) to relational databases, or Parquet files, an optimized format that stores data in columns together with their metadata (column names and data types).

The course script loads sales.csv, eleven sales with date, product, value and customer id, and works on it with the DataFrame API and with SQL:

sales = spark.read.option("header", True).option("inferSchema", True).csv("sales.csv")
sales.select(sales["product"], sales["value"]).show(2)
sales.filter(sales["value"] > 200).show()
sales.groupBy("product").sum("value").show()
sales.createOrReplaceTempView("sales")
spark.sql("select product, sum(value) as qt_tot from sales group by product")

A DataFrame registered with createOrReplaceTempView becomes a temporary table that lives as long as the session; spark.catalog.dropTempView removes it. saveAsTable instead materializes the DataFrame as a persistent table in the Hive metastore, the catalog where Hive keeps its table definitions (Spark creates a local one, based on the Derby database, if no Hive installation exists): the table survives restarts as long as you connect to the same metastore.
