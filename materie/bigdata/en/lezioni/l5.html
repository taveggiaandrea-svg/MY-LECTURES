How do you store a file bigger than any disk?

Hadoop, the Big Data "ecosystem": the HDFS distributed file system, the MapReduce computation engine, and the tools built on top of them.

Lesson 4 named the two main Big Data tools, Hadoop and Spark, and recalled the vocabulary of distributed systems: a node is a single server, a rack a case with a bunch of servers, a cluster a collection of servers, in one or more racks, that behaves as a single machine. This lesson opens Hadoop.

Hadoop. A distributed calculation system based on two components: HDFS (Hadoop Distributed File System), which stores the data, and MapReduce, a distributed calculation framework, which computes on them.

Hadoop is open source, distributed and scalable up to thousands of nodes, and handles both structured and unstructured data. It is also fault tolerant: it is built to run on commodity hardware, cheap ordinary servers that do break, and it survives their failures by keeping copies of the data. How?

Cut the file into blocks, then copy each block

Each file in HDFS is made of parts called blocks, generally 64 or 128 MB each. Each block is replicated: the default replication factor is 3, and it can be changed. The copies live on different nodes, so no single disk holds the whole file and no single failure destroys it.

A server called the name node holds all the file system metadata: the list of files, the list of blocks of each file, and their locations. It is the master node of the cluster: it handles operations such as creating, renaming and deleting files, and it takes care of replication. The other nodes are the data nodes, the slaves, which carry out the actual reads and writes.

What if a whole rack goes dark?

Replication protects the data until all the nodes holding copies of the same block fail. A rack shares power and network, so it can fail all at once: three copies on three nodes of the same rack would vanish together. That is why HDFS is rack aware: it places the copies so that even if an entire rack fails, all the data is still available.

Copies on different racks turn a hardware failure into a non-event. The price is disk space: with replication factor n, a file takes n times its size.

Hadoop 3 replaces replication with a more space efficient algorithm called erasure coding (EC). EC adds some extra data to the blocks, encoded so that the system can use it to rebuild other blocks if they become unavailable. According to the lecture it cuts the storage overhead, the extra space beyond the file itself, to 50%. A note on the slide: in Hadoop 3 erasure coding is an option enabled folder by folder, while replication with factor 3 remains the default.

Moving the computation to the data

Storing is half the job. MapReduce is the distributed computation engine that works on the data stored in HDFS. Today Hadoop has other, more efficient engines, but they all derive from MapReduce, which only has a Java API. The programmer must split the problem into two phases.

Map and reduce. In the map phase the data are prepared and mapped to a key/value structure: the output of the mapper program is a set of key/value pairs. In the reduce phase the actual calculation is performed: the output of the reducer is the final result, saved to an HDFS file.

The system does the rest. It runs the mapper on each node where parts of the input file are stored, so the computation travels to the data instead of the data to the computation. Then it sorts, shuffles and aggregates the mapper outputs, putting the values of the same key together, and runs the reducer on each node. The lecture's simplest example counts the letters of the input "A C B C A".

Word count is the first task of any text analysis, and the lecture runs it on a sentence from the Hadoop website. The mapper emits (word, 1) for every word; sort and aggregate collect the ones of each word; the reducer adds them up. Words are compared without capitals, so "The" and "the" are one key.

Built for batch, not for questions

MapReduce was designed for batch workloads: computations on a huge amount of data that complete in minutes or even hours. It is not suitable for interactive queries, the many small questions we send to an RDBMS (a relational database management system), where we expect an answer in seconds or tenths of a second. And it is hard to program: most problems are very difficult to express with a map and a reduce.

Pig and Hive make MapReduce easier. They offer high level languages and translate programs written in them into MapReduce jobs: Pig Latin is a procedural language whose instructions resemble SQL keywords, HiveQL an SQL dialect that implements the ANSI SQL syntax plus some built in functions. The main Hadoop distributions also provide ODBC drivers (a standard way for programs to connect to a database) that let users connect to Hive as if it were an RDBMS: every Business Intelligence and reporting tool can then reach Hadoop.

An ecosystem, not a program

Around HDFS and MapReduce grew a family of tools that cover the whole data life cycle. The lecture groups them in four layers.

The core services are HDFS, the engines MapReduce, Tez (which runs a job as a graph of steps rather than a fixed map and reduce) and Spark, and YARN (yet another resource negotiator), the software layer that allocates the cluster's resources to each Hadoop task and to the applications above it.

The data services include Hive, the SQL interface to Hadoop, which translates HiveQL into MapReduce, Tez or Spark programs; Pig, which does the same for Pig Latin; HBase, the NoSQL columnar database of lesson 4, which only works inside Hadoop; Storm and Flume, which ingest data produced in streams, such as server logs, tweets or IoT sensor readings; and Sqoop, a sort of ETL tool (extract, transform, load, lesson 1) between an RDBMS and Hadoop, which imports relational tables into Hadoop or exports data back. The diagram also shows HCatalog, which shares Hive's table definitions with the other tools (a gloss added here).

The operational services are Ambari, a web tool to manage the cluster; Oozie, a workflow tool to orchestrate jobs (MapReduce, Hive, Pig, Sqoop, Flume, Storm and so on); and Zookeeper, which shares and keeps synchronized the configuration files of each application.

The analytic tools are of three kinds. Some only work inside a Hadoop cluster: Giraph for graphs, Mahout for machine learning, Kylin for OLAP (the multidimensional analysis of lesson 1), which saves aggregations in HBase's columnar storage and uses them to answer Hive queries. Others are distributed tools of their own: Elastic Search, a powerful search engine, and Spark. Others connect to Hadoop from outside: SAS, KNIME (the tool of the second part of this course) and R.

Installing a cluster from the Apache distribution can be very hard, so companies use distributions with a semi-automatic installer; the most famous is Cloudera, which merged in 2018 with Hortonworks, another Hadoop distributor. On balance, Hadoop can handle every data type and store and compute huge amounts of data, but it is complex, difficult to install and maintain, and slow for some workloads such as interactive queries.

Is Hadoop still used?

Yes, but its role has shifted from default Big Data platform to installed enterprise infrastructure. It remains common in large organizations with mature on-premise or hybrid platforms (part in the company's own data centre, part in the cloud), especially where moving petabytes of data is expensive. MapReduce, however, is no longer central.

The new names, as the lecture defines them. Trino is a distributed SQL query engine that queries large data sets across different sources (S3, Hive, Iceberg, PostgreSQL and others) without moving them into one database. Flink is a distributed stream-processing engine that processes data continuously as events arrive, often in real time. Iceberg, created at Netflix, and Delta Lake, created by Databricks, the company of Spark's creators, are open table formats: they keep the data in files, usually Parquet, a columnar file format met again in lesson 6, plus metadata and transaction logs, so that several engines can treat the files as tables. Object storage means cloud services such as Amazon S3, Azure Blob Storage or ADLS Gen2, and Google Cloud Storage.

The usual Hadoop alternative is a data lake, or lakehouse, built with Spark on cloud storage: lesson 8 is about it. The lecture's advice to a data engineer in 2026 sums up the shift.

Kafka, which the lecture names here without detail, is a platform that moves streams of events between systems. The key idea: learn the Hadoop concepts (HDFS, name node and data nodes, partitioning, data locality, that is running the computation where the data are, YARN), because they explain why every modern distributed system looks the way it does, not MapReduce mastery.

Test yourself

If only one thing from this lesson stays with you: Hadoop splits files into replicated blocks spread across racks, and moves the computation to the nodes that hold them, map close to the data, then a shuffle, then reduce.
